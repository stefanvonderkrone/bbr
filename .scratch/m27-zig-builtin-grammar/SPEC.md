# M27 BuiltInGrammar expansion

Status: ready-for-agent
Milestone: M27

The [M27 brief](brief.md) records the approved decisions.
This spec turns the brief and the M27 section of [TODO.md](../../TODO.md) into buildable form.
The implementation tickets live in [issues](issues/).
The delivery model is [ADR-0009](../../docs/adr/0009-built-in-grammars-now-user-grammars-later.md).
The vocabulary comes from [the Highlighting glossary](../../src/highlight/GLOSSARY.md).

## Problem Statement

Reviewers review code in many languages.
bbr has 8 BuiltInGrammars today: JavaScript, TypeScript, TSX, CSS, Go, Bash, JSON, and YAML.
Every other File shows as plain text, unless the reviewer installs a UserGrammar.
A UserGrammar is native code with the user's permissions, and its installation takes effort.

Some Files contain more than one language.
Markdown has fenced code, HTML has `<script>` and `<style>`, and PHP sits inside HTML.
bbr highlights one Grammar for each File, so these Files are only partly highlighted.

## Solution

M27 adds 20 BuiltInGrammars, plus one BuiltInGrammar that only an Injection selects.
Each BuiltInGrammar uses the repository and the revision that nvim-treesitter pins.
Each highlight query comes from one pinned nvim-treesitter commit.
A tool copies the sources, adapts the queries, and records the checksums.
The build compiles only committed files and never generates or downloads a source.

`TreeSitterHighlighter` gets Injection.
A host BuiltInGrammar can give a region of a File to another BuiltInGrammar.
Markdown, HTML, and PHP use Injection.
The `Highlighter` seam does not change.

New Captures map to the existing Theme roles.
M27 adds no Theme color.
An active UserGrammar still takes precedence over every new BuiltInGrammar.
M27 measures the binary size before and after, and drops no Grammar for size.

## Vendoring procedure

### Read the nvim-treesitter pins

1. Clone `https://github.com/nvim-treesitter/nvim-treesitter` into a temporary directory.
2. Check out the pinned commit on the `main` branch.
3. Read the entry of the Grammar in `lua/nvim-treesitter/parsers.lua`.
   Its `install_info` table holds `url`, `revision`, and optional `location`, `branch`, and `generate` fields.
   Its `requires` list names other entries that the queries inherit.
4. Read the queries under `runtime/queries/<name>/`.
   M27 uses `highlights.scm` for every new BuiltInGrammar.
   M27 uses `injections.scm` only for the Injection hosts in "Injection".
   M27 does not use `locals.scm`, `folds.scm`, or `indents.scm`.

A `revision` can be a tag, such as `v0.23.5`.
The procedure resolves the tag to its commit and records both in the manifest.

### Source layout

A Grammar without `location` uses the M13 layout:

```text
vendors/tree-sitter/<name>/LICENSE
vendors/tree-sitter/<name>/src/parser.c
vendors/tree-sitter/<name>/src/scanner.c          (when present)
vendors/tree-sitter/<name>/src/tree_sitter/*.h
vendors/tree-sitter/<name>/queries/highlights.scm
vendors/tree-sitter/<name>/queries/injections.scm (Injection hosts only)
```

A Grammar with `location` keeps that directory:

```text
vendors/tree-sitter/<name>/<location>/src/...
```

A source can include a file outside its `src/` directory.
The PHP and XML scanners include `../../common/scanner.h`, for example.
The procedure copies each such file to its repository-relative path below `vendors/tree-sitter/<name>/`.
So the PHP scanner finds `vendors/tree-sitter/php/common/scanner.h`.
It never touches `vendors/tree-sitter/common/scanner.h`, which belongs to TypeScript.
An include that leaves `vendors/tree-sitter/<name>/` stops the procedure with an error.
The procedure never edits a vendored source.

### Generated parser.c

The procedure generates `src/parser.c` only when one of these conditions is true:

- The nvim-treesitter entry has `generate = true`.
- The pinned commit has no `src/parser.c` below the `location`.

Generation uses tree-sitter CLI v0.26.9, which matches the vendored runtime.
The command is `tree-sitter generate --abi 15` in the temporary checkout.
The procedure records the CLI version, the command, and the JavaScript runtime with its version in the manifest.
If the Grammar needs npm packages to generate, the procedure installs them only in the temporary checkout.
The procedure commits the generated `parser.c` and the generated `src/tree_sitter/*.h` files.
The build never runs the CLI.

### Licences

Each Grammar directory keeps the `LICENSE` file of its upstream repository.
A Grammar without a `LICENSE` file at the pinned commit stops the procedure.
The nvim-treesitter queries are Apache-2.0.
`vendors/tree-sitter/nvim-treesitter/LICENSE` holds that licence.
Each adapted query starts with a comment.
The comment names the source path and the commit, and states that bbr changed the query.
This meets the Apache-2.0 notice rule for changed files.

### Raw queries

The procedure copies each used upstream query unchanged to `vendors/tree-sitter/nvim-treesitter/queries/<name>/<kind>.scm`.
This includes inherited queries, such as `c`, `html_tags`, and `php_only`.
The adapted query in the Grammar directory is the output of the query adaptation from these raw queries.

### Manifest

`vendors/tree-sitter/manifest.zig.zon` gets one schema for every BuiltInGrammar.
Ticket 03 moves the 8 existing entries to this schema without a change to their files.

```zig
.nvim_treesitter = .{
    .repository = "https://github.com/nvim-treesitter/nvim-treesitter",
    .commit = "<40 hex>",
},
.tree_sitter_cli = .{ .version = "0.26.9" },
.grammars = .{
    .zig = .{
        .name = "Zig",
        .repository = "https://github.com/tree-sitter-grammars/tree-sitter-zig",
        .revision = "<revision from parsers.lua>",
        .commit = "<40 hex>",
        .location = null,
        .symbol = "tree_sitter_zig",
        .abi = 15,
        .generated = null, // or .{ .cli = "0.26.9", .command = "...", .js_runtime = "..." }
        .query_source = .nvim_treesitter, // .upstream for the 8 M13 Grammars
        .sources = .{ "zig/src/parser.c" },
        .highlights = "zig/queries/highlights.scm",
        .injections = null,
        .files = .{ .{ .path = "zig/src/parser.c", .sha256 = "<64 hex>" } },
        .matches = .{ .filenames = .{}, .extensions = .{ ".zig", ".zon" }, .shebangs = .{} },
    },
},
```

`.files` lists every vendored file of the Grammar, including headers, `LICENSE`, and raw queries.
`.symbol` is the exported `tree_sitter_<name>` function in `parser.c`.
`.abi` is the `LANGUAGE_VERSION` value in `parser.c`.

### The vendoring tool

`tools/vendor_grammar.py` runs the procedure for one Grammar.
It takes the nvim-treesitter checkout, the Grammar checkout, and the name.
It does not use the network, so the caller clones both repositories first.
It verifies that the Grammar checkout is at the pinned commit.
It copies the files, generates `parser.c` when necessary, and runs the query adaptation.
It prints the manifest entry, and the caller adds the entry to `manifest.zig.zon`.

`tools/check_vendored_grammars.py` runs in `zig build test`, like `tools/check_xdg_reads.py`.
It fails in these cases:

- A file checksum differs from `.files`.
- A file under a Grammar directory is not in `.files`.
- An adapted query differs from a new adaptation of the raw queries.
- A manifest entry has no directory, or a directory has no manifest entry.

`vendors/tree-sitter/README.md` describes the procedure and the two tools.

## Query adaptation

`tools/adapt_queries.py` turns raw nvim-treesitter queries into the adapted queries.
`tools/vendor_grammar.py` and `tools/check_vendored_grammars.py` both call it.
The output is deterministic.
The adaptation reads S-expression forms with string and comment awareness.
It never uses a line-based text replacement.

### Inherits

A first-line comment `; inherits: a,b` names base queries.
A name in parentheses, such as `(jsx)`, is optional.
The adaptation resolves the names recursively and in order.
It puts each base query before the query that inherits it, like Neovim.
So a later pattern in the child query takes precedence.
It writes `; bbr: inherited from <name>` before each base query.
A missing required base query stops the adaptation.
A missing optional base query adds nothing.

### Predicates and directives

The adaptation sorts every predicate and directive into one of four groups.
Any other form stops the adaptation with the file, the line, and the form.
So an unsupported predicate always fails a test and is never dropped without a record.

| Form | Group | Result |
| --- | --- | --- |
| `#eq?`, `#match?`, `#is-not? local` | supported | Kept. bbr supports them today. |
| `#not-eq?`, `#not-match?`, `#any-of?`, `#not-any-of?` | supported | Kept. Ticket 02 adds them to `query_predicates.zig`. |
| `#has-ancestor?`, `#not-has-ancestor?`, `#has-parent?`, `#not-has-parent?` | supported | Kept. Ticket 02 adds them to `query_predicates.zig`. |
| `#set! priority N` and `#set! "priority" N` | supported | Kept. Ticket 02 adds pattern priority. |
| `#lua-match?` | rewritten | Becomes `#match?` with the Lua pattern translated to RE2. |
| `#not-lua-match?` | rewritten | Becomes `#not-match?` with the translated pattern. |
| `#contains?` | rewritten | Becomes `#match?` with the escaped literal alternatives. |
| `#set! conceal`, `#set! conceal_lines`, `#set! @capture url @capture` | removed | The directive goes, and the pattern stays. |
| `#offset!` in a highlight query | removed | The directive goes, and the pattern stays. |
| `#gsub!` in an injection query | removed | The directive goes. The Grammar name resolution does the same work. |
| Injection directives in an injection query | supported | See "Injection". |

The Lua pattern translation handles the classes `%a`, `%d`, `%l`, `%s`, `%u`, `%w`, `%x`, `%p`, and `%c`.
It also handles their upper-case complements, `%` escapes, sets, anchors, and the lazy `-` quantifier.
A `%b`, `%f`, or back reference stops the adaptation.
The adaptation escapes the result for a query string literal.
RE2 then compiles it through `query_regex.zig`, so an invalid translation fails `TreeSitterHighlighter.init`.

Each removal leaves a comment at its place, such as `; bbr: removed (#set! conceal "")`.
These comments are the adaptation record.
The check compares them byte for byte, so a new removal shows in review.

### Captures

The adaptation removes the capture names `@spell`, `@nospell`, `@conceal`, and `@conceal_lines`.
These names control Neovim features, not color.
If they stay, a later `@spell` pattern takes precedence over `@comment` and removes its color.
Each removal leaves a `; bbr:` comment.

Capture names that start with `_` stay in the query, because predicates use them.
Ticket 02 makes `RuntimePackage` mark them hidden.
`collectCaptureIntervals` skips a hidden Capture, so it produces no Span.

### Capture classification

`Capture.init` in `src/highlight/highlighter.zig` maps each Capture name to a `CaptureRole` once.
Ticket 02 adds dotted-prefix rules before the existing root rules.
The longest matching prefix wins.

| Capture name or prefix | CaptureRole | Reason |
| --- | --- | --- |
| `variable.member` | `property` | nvim-treesitter uses it for fields. |
| `tag.attribute` | `property` | M13 queries use `attribute` for the same role. |
| `tag.delimiter` | `punctuation` | The brackets of a tag. |
| `markup.heading` | `keyword` | Headings need strong contrast. |
| `markup.raw` | `string` | Inline code and code blocks. |
| `markup.link` | `string` | Link labels and destinations. |
| `markup.list` | `punctuation` | List markers. |
| `markup.quote` | `comment` | Block quotes. |
| `markup.math` | `string` | Math spans. |
| `module` | `type` | Namespaces and packages. |
| `character` | `string` | Character literals. |

Every other name keeps the existing root rules.
`markup.strong`, `markup.italic`, `markup.strikethrough`, `markup.underline`, `none`, and `diff` stay `unknown`.
An `unknown` Capture uses the default foreground.
M27 adds no `CaptureRole` and no Theme color.
The roles of all Capture names in the 8 M13 queries stay the same.

The classification also applies to UserGrammars, because they share `Capture.init`.

### Precedence

nvim-treesitter and bbr both give a later pattern precedence over an earlier pattern.
Ticket 02 adds pattern priority from `#set! priority N`.
The default priority is 100, so the M13 queries keep their current precedence.
`higherPrecedence` in `tree_sitter_highlighter.zig` compares in this order:

1. The higher priority wins.
2. The deeper Injection layer wins. The host layer has depth 0.
3. The later pattern wins.
4. The later match order wins.

The new supported predicates and the priority also apply to UserGrammar queries.

## Injection

### Scope

Injection is internal to `TreeSitterHighlighter`.
The `Highlighter` seam, `HighlightResult`, and `Span` do not change.

Only these BuiltInGrammars have an injection query:

| Host | Injection query sources | Required Injections |
| --- | --- | --- |
| `markdown` | `markdown/injections.scm` | `(inline)` and `(pipe_table_cell)` to `markdown_inline`. Fenced code by its info string. |
| `markdown_inline` | `markdown_inline/injections.scm` | `(html_tag)` to `html`, combined. |
| `html` | `html_tags/injections.scm`, then `html/injections.scm` | `<script>` to `javascript`. `<style>` to `css`. |
| `php` | `php_only/injections.scm`, then `php/injections.scm` | `(text)` to `html`, combined. |

The adaptation keeps an injection pattern when its static Grammar name equals a BuiltInGrammar name in the manifest.
It also keeps every pattern with an `@injection.language` capture.
It removes a pattern with any other static name, such as `comment`, `regex`, `latex`, and `phpdoc`.
Each removed pattern leaves a `; bbr:` comment.

So some extra Injections come for free.
Examples are YAML and TOML front matter in Markdown, the `style` attribute in HTML, and PHP heredocs.
The tests cover the required Injections and one extra Injection.

A UserGrammar never takes part in an Injection.
It is never a host, and it is never an injected Grammar.
A fenced `js` block in Markdown uses the JavaScript BuiltInGrammar, also when a UserGrammar claims `.js`.

### Supported injection query forms

| Form | Meaning |
| --- | --- |
| `@injection.content` | The node whose text the injected Grammar highlights. |
| `@injection.language` | A node whose text is the Grammar name. |
| `#set! injection.language "<name>"` | A static Grammar name. |
| `#set! injection.combined` | All matches of the pattern with the same Grammar form one injected tree. |
| `#set! injection.include-children` | The content includes the ranges of the child nodes. |
| `#offset! @injection.content r1 c1 r2 c2` | Moves the start and end points of the content by rows and byte columns. |
| `#eq?`, `#match?`, `#any-of?`, and the other supported predicates | Filter the match, as in a highlight query. |

`query_predicates.zig` accepts these directives only in an injection query.
A highlight query with an injection directive still fails with `unsupported_directive`.
`Diagnostic.QueryKind` gets `.injections`.

### Grammar name resolution

A new C-free file `src/highlight/grammar_name.zig` holds one alias table.
`bbr.highlight.grammar_name` exports it from `src/root.zig`.
`code_highlighting.fencePath` in `src/tui/code_highlighting.zig` uses the same table.
So a ReviewBody fence and a Markdown Injection resolve a name the same way.

The adapter resolves a name in this order:

1. Make the name lower case.
2. Keep only the part after the last `/`. So `text/javascript` becomes `javascript`.
3. Select the BuiltInGrammar whose enum tag equals the name, such as `c_sharp` or `markdown_inline`.
4. Look up the name in the alias table, such as `js`, `py`, `c++`, `c#`, `kotlin`, `make`, or `docker`.
   An alias gives an extension.
5. Select with `grammar_match.selectBuiltIn` for the path `injection.<extension>`, or `injection.<name>` without an alias.
6. Otherwise, the match has no Injection.

Ticket 01 adds these aliases to the existing table: `kotlin` to `kt`, `make` and `makefile` to `mk`, `docker` and `dockerfile` to `dockerfile`, `markdown` and `md` to `md`, and `c_sharp` to `cs`.
The existing case `kOtLiN` in "M23 highlighting approved fence aliases and invalid identifiers" changes from `review.kotlin` to `review.kt`.

### Algorithm

`RuntimePackage` gets an optional prepared injection query and the ids of `injection.content` and `injection.language`.
It also gets the per-pattern injection settings from the directives.
`highlightWithPackage` in `tree_sitter_highlighter.zig` runs these steps:

1. Parse the File and collect the host intervals, as today.
2. Run the injection query on the host tree.
3. For each match, resolve the Grammar name. Skip a match without a BuiltInGrammar.
4. Compute the content ranges.
   Without `include-children`, a range is the node range minus the ranges of its children.
   An `#offset!` moves the range.
   A range that becomes empty, inverted, or splits a UTF-8 code point is dropped.
5. Group the ranges into layers.
   A combined pattern gives one layer for each host layer and Grammar.
   Every other match gives its own layer.
6. For each layer, call `ts_parser_set_included_ranges` with the sorted ranges and parse the full content.
7. Collect the intervals of the layer with the package of the injected Grammar.
   Clip each interval to the layer ranges, and split it where a gap falls.
8. Repeat steps 2 to 7 for each layer, to a maximum depth of 4.
   Markdown to Markdown inline to HTML to JavaScript needs a depth of 3.
9. Merge all intervals with `mergeCaptureIntervals`.

Each `CaptureInterval` carries its resolved `Capture`, its priority, and its layer depth.
It no longer indexes `package.captures` during the merge.
Two adjacent Spans join only when their Captures are equal.
So a Span keeps the Capture of the query that produced it.

### Span contract

Injected Spans keep the existing Span contract:

- Spans are ordered and do not overlap.
- Each Span is a half-open UTF-8 byte range within one Line.
- No Span endpoint splits a UTF-8 code point.
- An injected Span never covers a byte outside its layer ranges.

### Failure behavior

An allocation failure, a parse failure, or `QueryMatchLimitExceeded` in a layer fails the whole highlight of that File side.
This matches the M13 behavior for one layer.
A dropped range or an unknown Grammar name is not a failure.

## Build

`addTreeSitter` in `build.zig` compiles the sources and embeds the queries of every BuiltInGrammar from one list.
The preferred list is the manifest, imported into `build.zig` as ZON.
If a ZON import in `build.zig` is not practical in Zig 0.16, the list is `build/builtin_grammars.zig`.
In that case, `tools/check_vendored_grammars.py` also checks that this list equals the manifest.
Use the `zig` skill to verify the ZON import API before the choice.

Each Grammar keeps `-std=c11`.
A Grammar that needs another flag records it in its manifest entry.
The anonymous imports are `<name>_highlights` and `<name>_injections`.
`grammarSource` in `tree_sitter_highlighter.zig` keeps an exhaustive switch, so a new enum tag without a source is a compile error.
The `extern fn tree_sitter_<name>` declarations use the manifest `.symbol`.

`TreeSitterHighlighter.init` still prepares every BuiltInGrammar query at startup.
So an invalid query still fails at startup and in every test that creates the adapter.
Ticket 12 measures the time of `TreeSitterHighlighter.init`.

## ADRs

ADR-0009 holds.
M27 keeps the hermetic delivery: pinned, vendored, checksummed, and compiled into the executable.

Ticket 12 adds ADR-0014 "BuiltInGrammar queries come from nvim-treesitter".
It records these decisions:

- New BuiltInGrammars use nvim-treesitter queries, and the M13 Grammars keep their upstream queries.
- An adaptation tool rewrites or removes Neovim-only forms and leaves a record.
- A generated `parser.c` comes from one vendoring run with a pinned CLI, never from the build.
- Injection is internal to `TreeSitterHighlighter`, and UserGrammars take no part.

ADR-0009 says that sources are copied.
A generated Swift `parser.c` is not a plain copy.
ADR-0014 states this as a refinement of ADR-0009, not a reversal.

ADR-0003 holds.
The `Highlighter` seam and the core `bbr` module stay C-free.

## Testing Decisions

A good test asserts the Spans and the Capture roles that a reviewer sees.
Tests do not assert private interval layouts or the order of internal parses.
Every new Zig test name starts with `M27 grammar` or `M27 injection`.
`zig build test-builtin-grammars` runs the tests with the filter `M27`.

### Seams

- `TreeSitterHighlighter.highlighter().highlight` is the main seam.
  Fixtures pass a path and inline content and inspect the Spans.
- `highlightWithQuery` in `tree_sitter_highlighter.zig` tests synthetic queries on existing Grammars.
- `grammar_match.selectBuiltIn` is the GrammarMatch seam.
- `tools/adapt_queries.py` has its own Python unit tests with inline query text.

### Prior art

- "JavaScript BuiltInGrammar executes conditional Captures" and the `expectSpan` helper.
- "interval merge matches byte planes for every BuiltInGrammar fixture" and `spansFromBytePlanes`.
- "Grammar validation atomically rejects unsupported predicate forms".
- "UserGrammar runtime failure restores BuiltInGrammar or plain text" for a fixture registry.
- "M23 highlighting approved fence aliases and invalid identifiers" in `src/tui/code_highlighting.zig`.
- `tests/check_box_glyphs_test.py` for a Python check with its own test.

### Test plan

Query pipeline:

- Each new predicate accepts and rejects a match, on a synthetic JavaScript query.
- `#set! priority` changes the winner between two overlapping patterns.
- A highlight query with an injection directive fails with `unsupported_directive`.
- A `_` Capture produces no Span.
- The Capture classification table maps each listed prefix to its role.
- Every Capture name in the 8 M13 queries keeps its role.
- The adaptation resolves nested and optional `; inherits:` lines in order.
- The adaptation rewrites `#lua-match?`, `#not-lua-match?`, and `#contains?`.
- The adaptation translates each Lua class, and it rejects `%b` and `%f`.
- The adaptation removes `conceal`, `url`, and `#offset!` directives and leaves `; bbr:` comments.
- The adaptation removes `@spell` and `@nospell`.
- An unknown predicate stops the adaptation with the file and line.
- The check fails on a changed checksum, an unlisted file, and a hand-edited adapted query.

Injection, with existing Grammars:

- A synthetic JavaScript injection query injects CSS into a template string.
- A combined injection forms one tree from two separate ranges.
- Without `include-children`, a child node range gets no injected Span.
- `#offset!` moves the range, and an invalid offset drops only that Injection.
- Depth stops at 4 for a self-injecting synthetic query.
- Injected Spans equal the byte-plane oracle with layer depth and priority.
- A deeper layer wins at equal priority, and a higher host priority wins over a deeper layer.
- An unknown Grammar name gives no Injection and no failure.
- A UserGrammar never becomes an injected Grammar.

Grammars:

- Every BuiltInGrammar loads its queries.
- Every ABI is in range and equals the manifest.
- Each new Grammar has a Capture fixture.
  It asserts the comment, string, keyword, function, and type or constant roles that the language has.
- Each Grammar fixture joins the byte-plane oracle test.
- Each GrammarMatch row has a case for each filename, extension, and shebang.
- `.h` selects C++, and `.c` selects C.
- `#!/usr/bin/env python3`, `#!/usr/bin/ruby`, and `#!/bin/sh -e` select Python, Ruby, and Bash.
- A UserGrammar for `.zig` takes precedence over the Zig BuiltInGrammar.
- `bbr grammar check` reports Zig as an affected BuiltInGrammar for a `.zig` UserGrammar.

Required Injections:

- HTML `<script>` content has JavaScript Spans, and `<style>` content has CSS Spans.
- `<script type="text/javascript">` content has JavaScript Spans.
- Markdown headings and inline code have Spans from `markdown_inline` and `markdown`.
- A Markdown fenced `zig` block has Zig Spans, and a fenced `unknown` block has no injected Spans.
- A fenced block inside a block quote has no injected Span on the `>` marker.
- HTML inside Markdown has HTML Spans.
- PHP `<?php ... ?>` code has PHP Spans, and the HTML around it has HTML Spans.
- A `<script>` inside a PHP File has JavaScript Spans.
- YAML front matter in Markdown has YAML Spans.

### Required checks

- `zig fmt --check build.zig src`
- `zig build`
- `zig build test-builtin-grammars`
- `zig build test --summary all`, and the reported test count increases.
- `python3 tools/check_vendored_grammars.py .`
- `python3 tests/adapt_queries_test.py`
- `python3 tools/check_agent_docs.py`

It does not gate the hermetic suite.

## Further Notes

- Risk: two scanners can export the same global symbol, and the link then fails.
  The vendoring procedure must not edit a source, so a conflict needs a decision from a human.
- Risk: the clean build time and the binary size grow a lot.
  C#, C++, Kotlin, Swift, and SQL have large generated sources.
  Ticket 12 measures both, and the brief sets no limit.
- Risk: a Markdown File with many paragraphs creates many small injected trees.
  Ticket 10 records the highlight time of a large Markdown fixture.
- The fence alias table and the Injection share one resolver, so ReviewBody fences gain every new BuiltInGrammar.
- The M17 native-code warning for UserGrammars stays.
