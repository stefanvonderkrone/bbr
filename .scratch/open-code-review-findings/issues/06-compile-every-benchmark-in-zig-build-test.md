# Compile every benchmark in zig build test

Status: resolved
Blocked by: none

## Problem

`zig build test` does not compile the benchmark executables.
A change can break a benchmark, and the suite and CI still pass.

This happened twice:

- A compile error in `src/benchmark_file_cache.zig` passed the suite. Commit `4b6abe50` records this case.
- The origin codemod of PR 46 wrote `&presentation` in benchmark functions that take `presentation` as a pointer. `zig build bench-buffer-search` did not compile, and `zig build test` passed. Commit `b735a10e` fixed it.

Commits `4b6abe50` ("build: compile every benchmark in zig build test") and `68c4d678` ("build: add every benchmark through addBenchmark") fix this class.
Both are only on the branch `m28-full-review-file-cache-evaluation`, which is 60 commits ahead of `main` and not merged.

## Proposal

- Bring `4b6abe50` and `68c4d678` to `main` on their own, without the rest of the branch.
- `addBenchmark` makes each benchmark executable a dependency of `zig build test`, so a new benchmark cannot skip the compile step.
- Break one benchmark on purpose and check that `zig build test` fails.

## Acceptance criteria

- [x] `zig build test` compiles every benchmark executable in this change for `main`.
- [x] A compile error in a benchmark root makes `zig build test` fail.
- [x] `docs/rules/build-and-checks.md` has a rule section with an Enforcement paragraph for this check.
- [x] `zig build test` passes.

## Agent Brief

**Category:** enhancement
**Summary:** Make `zig build test` compile every benchmark executable, through one `addBenchmark` function in `build.zig`.

**Current behavior:**
`build.zig` creates the benchmark executables `bbr-bench`, `bbr-file-acquisition-bench`, and `bbr-buffer-search-bench` with `b.addExecutable`. The `test` step does not depend on them. A compile error in a benchmark root passes `zig build test` and CI.

Triage checked whether `4b6abe50` and `68c4d678` apply to `main`. They do not apply cleanly:
- `4b6abe50` conflicts in `AGENTS.md`. `main` now keeps rules in `docs/rules/`, not in `AGENTS.md`.
- `68c4d678` conflicts in `build.zig`. It also wires `bbr-file-cache-bench`, which exists only on `m28-full-review-file-cache-evaluation`, and it adds a ticket file of that branch.

So port the idea by hand. Do not cherry-pick.

**Desired behavior:**
- One function in `build.zig` creates each benchmark executable and makes the `test` step depend on its compile step. Its shape on the m28 branch is:

```zig
fn addBenchmark(b: *std.Build, test_step: *std.Build.Step, name: []const u8, root_module: *std.Build.Module) *std.Build.Step.Compile {
    const exe = b.addExecutable(.{ .name = name, .root_module = root_module });
    test_step.dependOn(&exe.step);
    return exe;
}
```

- Every benchmark on `main` uses it. `b.step("test", ...)` is at line 230 today, after the benchmarks, so it must move above them.
- The test step depends only on the compile step, not on a run of the benchmark. `bench-buffer-search` fails at runtime today, and ticket 04 tracks that.

**Key interfaces:**
- `build.zig`: the benchmark executables and the `test` step.
- `docs/rules/build-and-checks.md`: a new rule section, per `docs/agents/rule-areas.md`.

**Acceptance criteria:**
- [x] `zig build test` compiles `bbr-bench`, `bbr-file-acquisition-bench`, and `bbr-buffer-search-bench`.
- [x] With the past compile error restored in a benchmark function in `src/tui/presentation.zig`, `zig build test` fails. The ticket records the error text, and the error is then reverted.
- [x] No `b.addExecutable` call for a benchmark remains outside `addBenchmark`.
- [x] `docs/rules/build-and-checks.md` has a rule section with an Enforcement paragraph that names `addBenchmark` and the `test` step.
- [x] `zig build test`, `zig fmt --check src build.zig tests`, `python3 tools/check_agent_docs.py`, and `python3 tools/check_doc_symbols.py .` pass.
