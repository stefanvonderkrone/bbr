# Stabilize the Comments failure RawDiff test

Status: resolved
Blocked by: none

## Problem

The test "Comments failure prevents later RawDiff acquisition" in `src/tui/session.zig` failed once in CI:

```text
error: 'tui.session.test.Comments failure prevents later RawDiff acquisition' failed:
       expected 3, found 4
```

The failure was in the `test (macos-x86_64)` job of run 45015537323 for PR 42, on 2026-11-22.
PR 42 changed only `src/tui/presentation.zig`.
A rerun of the failed job passed.
No other failed run of the last 25 had this test.

The test releases fake HTTP responses through atomic flags and waits with `spinUntil`.
It expects that a failed Comments request stops the Session load before a fourth request, the RawDiff request, starts.
A count of 4 means that the RawDiff request started anyway.
It is not known whether this is a race in the test or a race in the Session load. That is a guess from one failure.

## Proposal

- Run the test in a loop on an x86_64 macOS host, or with the Zig thread scheduler under load, until it fails, and record the failure rate.
- Read the Session load to find out whether a RawDiff request can start after the Comments failure. If it can, the product has a race and the fix goes there. If not, the test waits on the wrong condition.

## Acceptance criteria

- [x] The ticket records how often the test fails before the fix, and the cause.
- [x] The test passes in a loop of at least 1000 runs.
- [x] `zig build test` passes.

**Category:** bug
**Summary:** The test "Comments failure prevents later RawDiff acquisition" waits on the wrong condition. Make it wait until the Session coordinator has seen the Comments failure.

**Current behavior:**

- 1000 runs without load gave 0 failures.
- 1000 runs with six `yes` processes as CPU load gave 5 failures, each `expected 3, found 4`.
- A 10 ms sleep before the status check of the Comments response gave 100 failures in 100 runs.

The test releases Comments, waits with `spinUntil(.active_request_count_not = 2)`, and then releases the account response (`src/tui/session.zig:850-852`).
`FakeHttpClient.send` drops the active count before its caller checks the HTTP status (`src/http/fake_client.zig:137-155`).
So the wait does not prove that the Comments completion reached the coordinator.
The account completion can reach the coordinator first and free a slot (`src/tui/session.zig:223-228`).
`required_failed` is still false, so the coordinator starts RawDiff (`src/tui/session.zig:239-248`).
Only the Comments completion sets `required_failed` (`src/tui/session.zig:234-236`).
In every forced trace, no request started after the coordinator saw the failure.

The product behavior is correct. The test is wrong.

**Desired behavior:**
- The test releases the account response only after the coordinator has consumed the Comments completion.
- The test still fails if a request starts after the coordinator has seen the Comments failure.
- The test name says what it checks.

- `FakeHttpClient` in `src/http/fake_client.zig`. A barrier or a counter of completed responses can go there, if the test needs it.
- Do not change the Session coordinator to suit the test.

## Completion

Commit `1445bbbf` fixes all three callers of the wrong wait in `src/tui/session.zig`.
It deletes the `active_request_count_not` arm from `TestWait` and `spinUntil`.
It also deletes the unused `loadFailureAndSignal` helper.
The Session coordinator does not change.
The review follow-up bounds each fake response gate at ten seconds.
A gate that stays closed returns `error.TestResponseGateTimeout`.

The active request count falls before the caller checks the HTTP status.
The old wait thus let another completion reach the coordinator before the required failure.
All three tests had this race.

The Session exposes no load state before `loadWith` returns.
The failed branch also exposes no coordinator-consumption signal.
A counter after `send` returns would still precede consumption.
`TestLoadSchedule` instead controls response release through an isolated `std.Io.Threaded` instance.
The helper changes only the test I/O vtable.
The helper checks the thread ID and the expected futex value.
A wait on the coordinator thread with expected value zero releases the next response.
The helper does not check the identity of the Condition or the queue.
In Zig 0.16.0, the next matching wait follows consumption of the previous completion.
The helper waits for an epoch change before it returns from a futex wait.
Thus a spurious wake cannot release the next response.
Cancellation releases all response gates before it joins the workers.

The helper depends on Zig 0.16.0 queue behavior.
The following paths are relative to the `lib_dir` from `zig env`.
`std/Io.zig:1470-1471` implements `Select.await` through `Queue.getOne`.
`std/Io.zig:2292-2295` reads one element through `Queue.get`.
`std/Io.zig:2122-2136` gives a blocked queue read a fresh Condition.
`std/Io.zig:1663-1666` initializes its epoch to zero.
`std/Io.zig:1592-1596` gives the mutex contention state value two.
`std/Io.zig:1612-1616` waits on that value.
The helper forwards waits with another expected value and all worker waits without a change.
A Zig upgrade can add another matching wait on the coordinator thread.
That wait can release a response too early.
The ten-second gate bound turns a missed wait into a test failure instead of an indefinite wait.
The tests keep their names because they still check the same request behavior.
Exact request counts detect a request after the coordinator consumes a required failure.
