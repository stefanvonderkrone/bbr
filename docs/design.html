bbr — Bitbucket Reviewer

A Zig terminal UI for reviewing Bitbucket Cloud pull requests.
Status · Design Zig · 0.16.0 TUI · libvaxis 0.6.0 Target · Bitbucket Cloud (workspace check24) Reference · ghostty

1 · Overview

bbr lets you review a Bitbucket Cloud pull request without leaving the terminal: open a PR by id or URL, browse its files in a sidebar, read the diff with proper coloring, view existing comment threads, and compose a batch of comments, replies, and suggestions that stay pending locally until you submit them together — after which they are published to Bitbucket via its REST API.

The design is shaped by three principles: deep modules behind narrow seams (so external dependencies and hard choices stay swappable and testable), correctness of comment anchoring by construction (never by luck), and a walking-skeleton delivery that is runnable end-to-end from the first milestone.

2 · Goals & Non-Goals

Goals

  • Open a PR by id or Bitbucket URL; fuzzy-switch between PRs.
  • File sidebar with change status and comment/draft counts.
  • Diff with neutral / green / red line backgrounds and emphasized intra-line changes.
  • Unified and side-by-side layout; changes-only and whole-file scope.
  • Read comment threads & replies inline on the diff.
  • Compose comments, replies, and suggestions as local drafts.
  • Submit drafts as one batch, with robust failure handling.
  • Show outdated & resolved comments — never hide them behind bare markers.
  • Local / offline review of a branch vs a base ref, no Bitbucket needed; git-worktree aware; open the adjacent PR from a checkout.
  • Vim motions (with numeric counts) alongside arrow keys.
  • Selectable themes (catppuccin / gruvbox / solarized / light / dark).
  • Syntax highlighting via tree-sitter (post-MVP).
  • Overlay windows (keybinding help, PR picker, composer).

Non-Goals

  • Bitbucket Server / Data Center support (different API).
  • Approving / merging / declining PRs (initially).
  • Applying suggestions — Cloud has no such endpoint; done in the web UI.
  • Editing files or running the code under review.
  • A general git client; bbr reads branches & diffs, it does not manage them.
  • Dirty working-tree diffs in local mode (MVP is committed refs only; deferred).
  • NTLM/Kerberos proxy auth in the first HTTP implementation (see §12).

4 · Architecture

bbr is split into five bounded contexts. Dependencies point inward toward the domain; the two contexts that touch the outside world (Bitbucket, and the SQLite side of Review) do so only through seams. The full glossary lives in each context's CONTEXT.md; the CONTEXT-MAP.md at the repo root records their relationships.

Two review modes, one pipeline A DiffSource unifies input: Bitbucket's RawDiff and local git diff both yield unified diff text, so the parser, renderer, and comment UI are mode-agnostic. Network work runs on a background thread pool and returns to the UI thread as events (§10). Each load is stamped with an Epoch; switching PRs bumps the epoch and stale results are discarded on arrival.

5 · Seams

Three dependencies are accessed only through a narrow vtable interface — the same type-erasure idiom as std.mem.Allocator. This keeps hard-to-reverse technology choices swappable and, crucially, makes the domain testable with fakes (see ADR-0003).

// http/client.zig — the networking seam. The Bitbucket adapter depends only on this.
pub const HttpClient = struct {
    ptr: *anyopaque,
    vtable: *const VTable,
    pub const VTable = struct {
        send:   *const fn (ptr: *anyopaque, a: Allocator, req: Request) anyerror!Response,
        deinit: *const fn (ptr: *anyopaque) void,
    };
    pub fn send(self: HttpClient, a: Allocator, r: Request) !Response {
        return self.vtable.send(self.ptr, a, r);
    }
};

6 · Domain Model

The core aggregate is a Diff for one PullRequest, whose line numbers come straight from Bitbucket (ADR-0001). Comments hang off those lines via an Anchor.

Diff
└── File { path, status, old_blob, new_blob }
    └── Hunk { old_start, new_start }
        └── Line { old_no: ?u32, new_no: ?u32, kind, in_hunk, segments: []IntraLineSegment }

LineKind      = enum { context, added, removed };   // "context" = unchanged
IntraLineSegment = struct { start: u32, len: u32, changed: bool };  // cosmetic emphasis

Anchor = struct { path: []const u8, commit: Hash,   // the commit it was authored on
                  from: ?u32, to: ?u32,             // old line / new line
                  start_from: ?u32, start_to: ?u32,  // multi-line range start
                  context: []const []const u8 };     // captured lines, for outdated display

AnchorState  = enum { current, moved, outdated };    // resolved vs the viewed diff
CommentTarget = enum { bitbucket, local };           // syncs+submits vs SQLite-only
Thread = struct { root: Comment, replies: []Comment, resolved: bool };

Draft = struct { local_id: TempId, kind: DraftKind, target: CommentTarget, anchor: ?Anchor,
                 parent: ?union{ draft: TempId, comment: CommentId },
                 body: []const u8, state: DraftState };
DraftKind  = enum { top_level, inline_comment, reply, suggestion };
DraftState = union(enum){ draft, submitting, posted: CommentId, failed: ApiError };
Key modeling decision A Reply's parent may be another Draft that has no server id yet. This is what forces topological ordering at submission time (§9).

7 · Diff & Rendering

Bitbucket's unified diff is the authoritative line model — we never recompute line numbers locally, because that would risk anchoring comments to the wrong line (ADR-0001). The only thing we compute ourselves is the intra-line word diff over adjacent removed/added pairs, purely to emphasize the changed characters.

Coloring

context (neutral) · added (green) · removed (red) · with a stronger shade on the exact changed span.

13- fetch(url, { retries: 3 });
13+ fetch(url, { retries: 5, backoff: true });

Two orthogonal view axes

The same Buffer is projected through a 2×2 matrix — no second data source, so switching any axis is instant (no refetch, no reparse).

Layout: UnifiedLayout: SideBySide
Scope: ChangesHunks + context inline, far context folded (expandable).Old left / new right, hunks only.
Scope: WholeFileEntire file, changes shown inline.Entire old file left / entire new file right.

A Fold collapses long runs of far-from-change context in Changes scope; expanding it reveals already-loaded lines and never refetches.

8 · Syntax Highlighting

Post-MVP, behind the Highlighter seam. The MVP renders plain text so the diff viewer works end-to-end on day one.

Non-obvious constraint You cannot reliably highlight a raw diff — hunks are fragments. We highlight the complete old and new file blobs (which we already fetch), then map per-token colors back onto diff lines. Highlighting produces foreground color only; the diff background is composed over it per cell. Two independent layers.

Engine: tree-sitter via Zig bindings. Initial grammar set: TS/JS + React (tsx/jsx), CSS, Go, Bash, JSON, YAML. Grammar delivery (build-time vendored vs. neovim-style runtime auto-fetch, which needs a cc) is a deferred decision — both live behind the same seam.

9 · Comments & Pending Review

Bitbucket Cloud publishes comments immediately — it has no native draft/pending concept. bbr therefore batches entirely client-side (ADR-0002): drafts accumulate in a PendingReview persisted to SQLite, and are published together on Submission.

Submission algorithm

  1. Topologically order drafts — a reply is posted only after its parent, because it needs the parent's server-assigned CommentId.
  2. POST each draft; remap local temp id → server id as responses return.
  3. On per-item validation failure, keep that draft and its reply-descendants pending; continue with the independent ones.
  4. Report a per-item summary: N posted · M failed (with reason) · retry?

Failure model

The Bitbucket adapter classifies every failure (transport error or non-2xx + parsed error JSON) into a typed ApiError; the classification, not the status code, drives the measure.

ClassRetryableMeasure
network, server (5xx)yesExponential backoff + jitter, capped attempts.
rate_limited (429)yesHonor Retry-After before retrying.
unauthorized / forbiddennoAbort the whole batch; keep everything pending; surface token/scope error.
bad_request (400/422)noItem-level fail with server message; skip its descendants; continue.
not_found (404) / conflict (409)noItem-level fail, surfaced with message.
Two sharp edges Duplicates: if a POST succeeds but the response is lost, an auto-retry could double-post — Cloud has no idempotency key. Guard: before re-POSTing after an ambiguous failure, GET the PR comments and skip if one already matches (path, line, content-hash).
Stale anchors: if the PR gets new commits after we loaded it, anchor lines may no longer exist (→ 400). Guard: capture the SourceCommit on load; re-check the PR head before submit and warn if it changed.

9b · Review Modes & Anchor Lifecycle

Two modes over one pipeline

SourceBitbucket RawDiff + blobsgit diff <base>..<branch> via GitClient
Commentssync from Bitbucket; Drafts submit as a batchpersist in SQLite; never submit (target = local)
AnchoringBitbucket line numbers authoritativecommit + line, mapped locally

From a checkout, Git reads the current branch (worktree-aware) and finds the AdjacentPullRequest (open PR whose source branch matches) — so you can jump from a local branch straight into its remote review, or review the branch offline. MVP local mode diffs committed refs only, so every anchor binds to a stable commit + line.

Startup resolution (run bbr in your repo)

  1. Explicit arg — bbr <pr-id> or bbr <url> opens it directly (overrides detection).
  2. Else inspect CWD via GitClient — if it's a git repo/worktree, read the current branch and the tracking Remote, parsed to (workspace, repo_slug). The parser handles SSH and HTTPS forms plus this machine's url.insteadof rewrites.
  3. Query Bitbucket for open PRs whose source branch matches, in that repo:
    • exactly one → open its remote review;
    • multiple → the PR Picker, pre-filtered to those;
    • none → the no-PR chooser: Pick a PR · Review branch locally · Quit.
  4. Not a git repo → the PR Picker (choose a repo first).

So startup detection needs a minimal, read-only GitClient (branch + Remote) available at M4 — earlier than the diffing GitClient that local review needs at M12.

Anchor lifecycle (answering "what about changes after the fact?")

Every Anchor binds to a commit + line (plus captured context lines). Against the currently-viewed diff a comment resolves to one of three AnchorStates:

current
line unchanged → inline
moved
line shifted by nearby edits → inline + marker
outdated
line gone → per-file "Outdated (N)" collapsible, using captured context
Who computes it (ADR-0005) Remote comments: display Bitbucket's own outdated verdict + original hunk — Bitbucket is authoritative for its comments (consistent with ADR-0001).
Local comments & pending drafts: no server, so we compute the state ourselves by diff-walking — git diff <anchor_commit> <current_ref> -- <path> maps the old line forward.

Outdated and resolved comments are never hidden. Resolved Threads sit behind a toggle that reveals the entire thread (comment + replies) — not a bare "a resolved comment exists here" marker.

Navigation & themes

A Keymap layer supports vim motions with numeric counts (hjkl, ctrl-d/ctrl-u, gg/G, zz, 5j) alongside arrow keys; it is config-driven and feeds the help overlay. The Theme (§8) is the single place color lives, so selectable palettes — catppuccin, gruvbox, solarized, plain light/dark — are a data change, not new render paths.

10 · Concurrency

  • Main thread owns the vaxis event loop, all rendering, and all mutable UI state — single-threaded UI, no UI locks.
  • Background work runs on std.Io.Threaded (0.16's threaded runtime; async_limit defaults to CPU-count−1). This is the same Io that backs std.http.Client, so we don't hand-roll a thread pool.
  • Workers deliver results by posting custom events into vaxis's event queue, so responses are handled in the same loop as keypresses — the model is mutated only on the main thread.
  • Epoch cancellation: each load carries a generation token; on PR switch we bump the epoch and drop stale results (and free their arena) on arrival.

In 0.16, std.http.Client requires an Io (it has an io: Io field), so std.Io.Threaded is the natural background runtime rather than a separate std.Thread.Pool. Everything network-facing still sits behind the HttpClient seam. See ZIG.md §2.

11 · Memory Model

Allocation is tiered by lifetime. Arenas are reset and reused, so switching files reuses backing pages instead of re-mapping them.

TierAllocatorHoldsReset on
GlobalGPA / c_allocatorconfig, HttpClient, SQLite handle, tree-sitter parsersprocess exit
PR-scopedarenaPR metadata, file list, comment threads, drafts cachePR switch
Buffer-scopedarena (.retain_capacity)one File's rendered model: lines, folds, segments, wrapping, spansfile switch (reused)
Two edges Multi-file view needs several buffers alive at once, so the buffer tier is an arena pool / ring (one arena per visible slot, LRU-recycled) — not a single arena.
Threads: arenas aren't thread-safe, so a worker parses into its own fresh arena and hands the whole arena + model to the main thread as the result event; the main thread swaps it into the buffer slot and destroys the previous arena. Arenas double as the unit of ownership transfer and epoch-cancellation cleanup.

12 · Auth & Security

  • Auth = HTTP Basic, Authorization: Basic base64(email:api_token), read from BITBUCKET_USERNAME / BITBUCKET_TOKEN / BITBUCKET_WORKSPACE.
  • The token is never logged and never persisted — not in SQLite, not in state files.
  • Proxy support: std.http.Client auto-reads HTTPS_PROXY/ALL_PROXY, does CONNECT tunneling, and supports Basic-auth proxies. It does not support NTLM/Kerberos or TLS-intercepting proxies — if check24's network needs those, we swap in libcurl behind the HttpClient seam (ADR-0003).
  • No NO_PROXY support in std; irrelevant for a single external host.

13 · Testing (TDD)

The seams exist partly so the domain is testable without network, disk, or a C toolchain. Red-green-refactor targets the pure logic first:

  • Diff parsing — feed FakeHttpClient canned unified-diff fixtures; assert the Line model, hunk boundaries, and line numbering.
  • Intra-line diff — table-driven cases over removed/added pairs → expected segments.
  • Thread building — flat comment list (with parents) → nested Threads.
  • Submission ordering — a draft graph → asserted POST order and temp-id remapping.
  • Failure handling — FakeHttpClient returns 401/429/400/5xx → assert abort vs. retry vs. mark-and-continue, and the dedupe guard.
  • Store — property-style round-trips through the in-memory PendingReviewStore, then the SQLite one.

Rendering is verified against a headless vaxis test surface (assert cell colors for a known Buffer).

14 · Milestones

Vertical slices — a thin runnable spine first, then widen. Small, coherent milestones: read-only precedes commenting (correct anchoring is a prerequisite for correct comments), and the pure diff parser and comment submission are each isolated so their risk is contained. 15 · Open Questions & Deferred Decisions

  • Grammar delivery — build-time vendored (fixed set, no runtime cc) vs. neovim-style runtime auto-fetch+compile (needs cc). Deferred to M11.
  • Corporate proxy type at check24 — determines whether libcurl is ever needed. Seam is ready either way.
  • Bitbucket rate limits — exact thresholds; tune pool size & backoff against observed 429s.
  • Config format & location — likely TOML at ~/.config/bbr/; finalize at M10.
  • Approve / merge / decline — currently a non-goal; revisit after M8.
  • PR-head re-check UX — reload vs. submit-anyway when the SourceCommit changed.
  • Dirty working-tree diffs (local mode) — deferred; needs fuzzy content-based anchoring. MVP is committed refs only.
  • Adjacent-PR ambiguity — behavior when a branch has multiple or zero open PRs.

Resolved during design: "changes after the fact" → the AnchorState lifecycle (§9b, ADR-0005); outdated comments → kept and shown, never hidden.
