# Agent guidance

## Agent skills

### Issue tracker

Issues and PRDs are tracked as local Markdown under `.scratch/`; external PRs are not a triage surface. See `docs/agents/issue-tracker.md`.

### Triage labels

Use the canonical `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, and `wontfix` states. See `docs/agents/triage-labels.md`.

### Domain docs

Read `GLOSSARY-MAP.md` for domain vocabulary and relationships. Read `docs/code-navigation.md` to find implementation owners. System-wide decisions live under `docs/adr/`. See `docs/agents/domain.md`.

### Agent checks and tools

After agent document or tracker changes, run `python3 tools/check_agent_docs.py`. See `docs/agents/tools.md` for project MCP defaults.

## Rules and enforcement

Each rule names the check that fails when you break it. A rule marked "convention (no check)" fails nowhere, so read it before you change that code.

| Rule | Enforcement |
| --- | --- |
| Release publication requires exactly four local target archives and `SHA256SUMS`. Every remote draft asset must have an expected name. Read all remote asset pages before the first write and again after upload. The final asset names must match the expected set. A failed final check stops publication. Reject unexpected assets without deleting them. | `python3 tests/publish_release_test.py`, run by CI. The tests cover incomplete local archives, unexpected remote assets before and during upload, missing final assets, pagination, and failed initial and final reads. |
| Choose `--latest` from the final remote snapshot after upload. Latest-release ordering compares only valid canonical `vYYYY.M.D-N` tags. An uncomparable latest tag permits publication with `--latest=false`. A malformed incoming release tag permits no publication. | `python3 tests/publish_release_test.py`, run by CI. The tests cover latest changes during upload, foreign latest tags, malformed dated tags, and valid dated ordering. |
| A List Overlay arm holds no pointer except the buffers it owns. Borrowed data, such as the Session's Files, comes in as an argument at each call. | The `comptime` block after `ListOverlay` in `src/tui/list_overlay.zig` (compile error). |
| The File Finder and the Command Palette close before Session replacement. | The exhaustive switch in `ListOverlay.closesOnReplacement` in `src/tui/list_overlay.zig` (compile error for a new arm). The tests "File finder opened during a replacement does not outlive the replaced Session" and "a Session replacement closes the Command Palette" in `src/tui/presentation.zig`. |
| A new List Overlay is one arm of the `ListOverlay` union in `src/tui/list_overlay.zig`. | The exhaustive switches in the `ListOverlay` methods (compile error). |
| An `OwnedCommand` converts to its launch-failure `OwnedInput` only in `OwnedCommand.launchFailed` in `src/tui/presentation.zig`. No arm frees its payload. | The exhaustive switch in `OwnedCommand.launchFailed` (compile error). The test "every OwnedCommand launch failure keeps its correlation and frees the command". |
| Each `ThemeId` has one built-in Theme with the same name. | The `comptime` block after `theme.value` in `src/tui/theme.zig` (compile error). The test "every ThemeId resolves to the built-in Theme of the same name". |
| Only `src/xdg.zig` reads `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_STATE_HOME`. Other code calls `xdg.configHome`, `xdg.dataHome`, `xdg.stateHome`, or `xdg.configFile`, which ignore an empty or relative base. | `tools/check_xdg_reads.py`, run by `zig build test`. It skips `test` blocks and `env.put(` lines. |
| A terminal surface is a View tree in `src/tui/layouts.zig`. Only `src/tui/view_paint.zig` paints borders, rules, junctions, Titles, and scroll bars. A content painter draws into a Slot's content rect. | `tools/check_box_glyphs.py`, run by `zig build test`. It fails on a border corner or junction glyph in `render.zig` or `app.zig` outside `test` blocks. |
| A Pane has rounded corners and its Title in the top border. Its body starts in the next row, with no rule under the Title. The Sidebar and the DiffPane touch, with no empty column between them. | The tests "focused Pane frames and File Tree tallies use Frame-owned geometry" in `src/tui/render.zig` and "the Panes touch with no gap and a 28-cell Sidebar" in `src/tui/layouts.zig`. |
| Every Title has one blank cell on each side, so its text never touches the border. A Title that a View tree cannot hold, such as the DiffPane path, goes through `view_paint.titleText`. A control that its owner paints, such as the Selected Version control, calls `view_paint.titleGaps`. | `view_paint.titleText` and `view_paint.titleGaps` add the blank cells and take no option to drop them. The tests "the painter joins a rule into its parent border and paints Titles and thumbs" in `src/tui/view_paint.zig` and "DiffPane title reserves and renders published Selected Version targets" in `src/tui/render.zig`. |
| Every Overlay surface has a rounded border. An input Overlay, which is every List Overlay and Review Search, builds its surface with `inputSurface` in `src/tui/layouts.zig`. That surface is a bordered input box above a bordered result box, with no outer border. Every other Overlay builds its surface with `overlaySurface`. A border has no square option. | `view.Border` has no corner field (compile error). The tests "every Overlay surface has a rounded border" and "an input Overlay is a bordered input box above a bordered result list" in `src/tui/render.zig`. |
| An Overlay paints the Theme's base background. Only content highlights, such as the selected entry, search marks, and diff and Review Card bands, carry their own background. | The `comptime` block after `theme.value` in `src/tui/theme.zig` (compile error). The test "every Overlay paints the Theme base background" in `src/tui/render.zig`. |
| A new Composition is one arm of the `Composition` union in `src/tui/view.zig`. | The exhaustive switch in `view.walk` (compile error). |
| A layout tree places each of its Slots exactly once. | The assertions in `view.Solver`. The test "every layout places each of its Slots" in `src/tui/layouts.zig`. |
| A layout tree always declares its scroll bars, and only the scroll numbers vary. Presentation solves a tree without the numbers, so a scroll bar that comes and goes would move a padding or margin ring between hit testing and paint. | Convention (no check). `layouts.Scroll` is not optional in the existing trees. |
| `presentation.zig` does not import vaxis or `theme.zig`. The Theme reaches Presentation only as a `ThemeId`. | Convention (no check). `presentation.zig` imports `keymap.zig`, and `keymap.zig` imports vaxis. |
| A File Jump calls `Published.jumpToFileHeader` in `src/tui/presentation.zig`. It puts the File header on the top DiffPane row, and Nav clamps the scroll at the end of the Buffer. A File Jump from the File Tree moves focus to the DiffPane. | The test "every File jump puts the File header on the top DiffPane row and the File Tree cursor on the File" in `src/tui/presentation.zig`. |
| While the DiffPane has focus, the File Tree cursor follows the active File. `revealActiveFile` moves it, and keyboard, mouse, and view-build paths all call `revealActiveFile` when the active File changes. | The tests "every File jump puts the File header on the top DiffPane row and the File Tree cursor on the File" and "M21 kernel active File reveal without collapsed ancestors needs no allocation or Buffer rebuild" in `src/tui/presentation.zig`. |
| The status paints each part through `Theme.statusStyle` in `src/tui/theme.zig`. Every cell has the status bar background, and the bar follows the Theme polarity: a dark bar with light text in a dark Theme, a light bar with dark text in a light Theme. A new part is one arm of `StatusPart`. | The exhaustive switch in `Theme.statusStyle` (compile error). The tests "the status follows the Theme polarity and emphasizes its parts" and "the status colors each Reviewer Verdict, Buffer Search miss, and busy state" in `src/tui/app.zig`. |
| The status region is the meta part above the hint part. Each part wraps by item, never inside an item. Its height comes from `layouts.statusHeight` in `src/tui/layouts.zig`, and `syncContentGeometry` in `src/tui/app.zig` sends Presentation the content geometry that remains. The position item takes the width of `total/total`, so a cursor move never changes the height. | The tests "the status parts wrap by item and stack the hints under the meta information" in `src/tui/layouts.zig`, and "the status puts the meta items above the hint items and separates items on one row", "the status height does not change when only the cursor moves", and "content geometry leaves the rows the status needs" in `src/tui/app.zig`. |
| A ReviewCard has a rounded border with its Title in the top border and its disclosure footer as the Title in the bottom border. `drawReviewCard` in `src/tui/render.zig` maps each `review_card.Part` to a `view_paint.CardEdge`, and `view_paint.cardEdge` paints it. Only the thread root of the Active Path, the card that holds the cursor and its ancestors, has an Anchor Indicator. It runs in column 0 from `╭` on the root's top anchored Diff Line over every row between, such as other cards and other anchored lines, to `╰` on the root's top border row, and the root's top-left corner in column 1 becomes `┬`. `Buffer.activePath` in `src/tui/buffer.zig` names the rows, and `view_paint.anchorIndicator` and `view_paint.anchorCorner` paint them. A cursor outside a card shows no indicator. A Reply, a File-level card, and a Review-level card have none. Every card starts one column right of its depth indent, so column 0 stays free for the indicator: `CardIndentation.offset` adds `frame.anchor_cols`, and each gutter starts at `frame.anchor_cols`. A card on the Active Path paints its border, Title, joins, and the rails that lead down to a path card in the border style of its role. Every other card paints them in `Theme.card_border_dim`. A Reply starts directly below the preceding card, with no blank row. `drawReviewCard` uses `view_paint.join`: the border row directly above the Reply gets `┬`, or `├` on a `╰` corner, and the Reply's top-left corner becomes `├`. A cell that holds no line, such as a disclosure footer Title, stays as it is. A join cell keeps the style of the border that holds it, so a `┬` on an Active Path card stays in the normal border style when its Reply is dim. A card with a later sibling keeps its line down to that sibling: `drawReviewCard` joins its bottom-left corner with `├`, and `view_paint.rail` paints `│` in that column, only in a blank cell, on every row between the card and the sibling. `indexCards` in `src/tui/buffer.zig` sets `ReviewCardRow.sibling_below` and `ReviewCardRow.rails` after it weaves. | The exhaustive switches in `drawReviewCard` and `Part.isBorder` in `src/tui/review_card.zig` (compile error for a new Part). The tests "M23 ancestry ReviewCards have rounded borders, Titles, an anchor indicator, and no Reply gaps", "M23 ancestry only the active path shows its Anchor Indicator", "M23 ancestry a Reply joins the border above with ┬ and its own top-left corner with ├", "M23 ancestry a Reply join never overwrites the disclosure footer Title", and "M23 ancestry a Reply with a later sibling keeps its line down to that sibling" in `src/tui/render.zig`. |
| A resolved Thread header is the exception to the dim border outside the Active Path. Its rule or root top border stays bold green. The expanded root header replaces the collapsed disclosure row and retains its disclosure identity. | The tests "M23 ancestry resolved Thread header replaces its disclosure while independently expanded" in `src/tui/buffer.zig`, "M23 ancestry resolved Thread disclosure names its author in bold green text" in `src/tui/render.zig`, and "Session disclosures toggle independently persist through rebuilds and reset atomically" in `src/tui/presentation.zig`. |
| The Buffer owns shared ReviewCard geometry and rail nodes. Active Path lookup follows parent links and indexes roles by depth. Each rail chain has one node per distinct column. The shallowest rail owns a column when indentation reaches its limit. | The tests "ReviewCard rail storage stays linear in Reply count", "Active Path lookup needs only the cursor row and shared card geometry", "hidden Draft parents keep separate card trees and sparse Active Path depths", and "ReviewCard metadata construction releases every failed arena" in `src/tui/buffer.zig`. The test "sibling rails use the Active Path role past more than one sibling" in `src/tui/render.zig`. |
| A ReviewCard paints the Theme's base background on every row, for every CardRole: borders, Titles, body, and footer. A role differs from another role only by its foreground and emphasis. Only content highlights carry their own background: the code and Suggestion rows that `Part.hasCodeBackground` names, search marks, and the cursor band. | The `comptime` block after `theme.value` in `src/tui/theme.zig` (compile error that names the Theme, role, and Part, or the field `card_border_dim`). The tests "a ReviewCard paints the Theme base background" in `src/tui/render.zig` and "the dim card border differs from every normal card border in every built-in Theme" in `src/tui/theme.zig`. |
| When the cursor is in a ReviewCard, only the anchored Diff Lines of its thread root carry the Ancestry Band from `Theme.ancestryBg`. Parent Comments and Drafts keep their normal background. `ActivePath.banded` in `src/tui/buffer.zig` names the rows from the same `Buffer.activePath` that decides the Anchor Indicator and the border styles. The cursor's own card keeps the stronger cursor band. | The tests "M23 ancestry the dim band covers only anchored Diff Lines and leaves parent cards unchanged" in `src/tui/render.zig` and "the ancestry band differs from the plain and cursor backgrounds in every built-in Theme" in `src/tui/theme.zig`. |
